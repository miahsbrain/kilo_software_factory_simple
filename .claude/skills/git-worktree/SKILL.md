# Git Worktree

Anchor writes to the user-approved workspace: verify resolved control and target repo/worktree/app roots against the assignment before mutation; stop on mismatch. Never enter siblings, infer destinations from display/service names or reuse unrelated board/worktree paths without explicit approval. Lifecycle helpers may still run from app/feature worktrees and restore from the factory. Project creation alone requires source factory-root CWD, defaults to local `project/`, and requires actual user approval before external `--destination` plus project-only `--allow-outside` (capability, not consent).

Use the assigned workspace for implementation, docs, fixes, and review. All FEATURE implementation requires an assigned linked worktree, not the primary checkout. Explicitly assigned features may share that worktree and branch; preserve scope/ownership and never auto-switch branches. Inspect existing links before creating anything. Tracked `services.json` records only service names/paths/Git ownership; ignored `.claude/repos.json` maps control plus actual separate repos using full service-name IDs. Project Git is mandatory; service ownership and role are explicit: follow the approved plan's full name, role, sibling `apps/<full-name>` root, responsibility/stack and separate/project ownership, asking actual unknown decisions. Use `bootstrap.py app <product-role> --role <role> --git separate|project` from the assigned linked control source worktree root, invoking the actual inherited primary-control or approved factory script path. Names must end in `-<role>` with a valid nonempty product prefix; any safe lowercase kebab-case role is supported, including multiword roles, not an enum. Do not collapse planned services or infer unapproved services from technology. Separate mode initializes/initial-commits/maps; project mode has no nested Git/staging/control commit and adds a targeted source unignore. Both register ownership in the unchanged three-field manifest; operational topology/roles belong in product docs, not a registry. Legacy entries/restores are not renamed or inferred. Verify implementation assignment: project-tracked services use control's worktree; separate services their full-name mapped worktree.

New-project metadata gets its initial commit before the first board/task control assignment. Create/resume that linked assignment with this lifecycle before registering apps; bootstrap checks board linkage, active metadata and actual Git/common-directory/branch identity, never creates assignments or falls back to primary. Tracked `services.json`, project-owned app source and targeted `.gitignore` edits stay source-local; primary tracked files/index/HEAD stay untouched. Separate repos retain Git-derived canonical primary-control `apps/<full-name>` roots, never feature-worktree nested repos: check printed canonical targets against the approved assignment first. Inherit ignored config/harness; do not copy secrets/config just to invoke bootstrap.

Registration safely unions ignored canonical/source maps and primary/source manifest registrations, retaining other branches' separate full-name IDs. Divergent ownership/paths, stale/noncanonical maps and existing/partial/symlink targets refuse before writes. Only the caller's local snapshot refreshes; lifecycle resolves against the canonical map. This is not a tracked manifest merge: restore uses the persisted primary manifest after an explicitly authorized registration merge/commit, never switches/merges branches implicitly, and fresh clones do not recover unmerged registrations from ignored maps.

Use the existing scripts from the control root:

Both modes write safe app-local project-ignore snapshots without control service-directory rules. Source/docs remain trackable; harness/config/devcontainer/generated root instructions/live board/secrets/outputs stay local ignored. Later ignore changes do not automatically refresh snapshots.

```bash
python3 .claude/skills/git-worktree/scripts/worktree.py mode status
python3 .claude/skills/git-worktree/scripts/worktree.py reviews status
python3 .claude/skills/git-worktree/scripts/worktree.py list
python3 .claude/skills/git-worktree/scripts/worktree.py resume --board <ID>
python3 .claude/skills/git-worktree/scripts/worktree.py create --board <ID> --repo <repo-id> --base <branch>
python3 .claude/skills/git-worktree/scripts/worktree.py create --board <NEW-ID> --reuse <EXISTING-ID> --repo <repo-id>
```

`reviews status` reads independent automatic `qa` and `ui` booleans (both default on). Check from the assigned root before review delegation and again in the reviewer. An unreadable or invalid result requires manual review; do not change policy to unblock automation. See the QA skill for capture limits and the mandatory skipped-scope checklist link at completion. These switches do not disable ordinary code tests or change board lanes.

Create only an authorized workspace. `--reuse` supports Feature rows as well as Fix rows, retaining the existing branch/base and recording the new assignment. Feature implementation always needs an assigned linked worktree. Bootstrap's one initial commit in a genuinely new repository precedes feature assignment.

| Saved mode | `create --skip-worktree` | Ordinary primary-checkout edits | Guarded primary-checkout commits |
|---|---|---|---|
| `required` (default for new state) | Refused for every row | Ask | Refused |
| `optional` | Eligible Fix, Chore or Docs only | Allow by default | Existing named, nonprotected branch only |
| `adaptive` | Eligible Fix, Chore or Docs only | Ask | Refused: Git has no board-row context |

From the assigned mapped repository's primary checkout, run `worktree.py create --board <ID> --repo <repo-id> --skip-worktree` for an explicitly assigned maintenance edit. It checks the row is Ready/In Progress, has no workspace assignment or blocker, and the current branch is named and nonprotected. A pass prints the checkout and branch; it **does not** create, switch, record a workspace, change mode, grant edit/commit approval, or provide a merge handoff. Choose a linked worktree from the start if adaptive work needs a commit or managed handoff.

Static edit permissions and bare Git commands cannot identify a task type. The board-aware skip check enforces task eligibility; do not treat an optional permission default as authorization for Feature work. Protected-file and secret rules remain in force in every mode. Read the current mode with `mode status`; only a separately authorized `mode required|optional|adaptive` changes the project-local setting. The guard hook reads it on every tool call, so no restart or config regeneration is needed; never toggle mode for one task.

Reuse first: the same task's metadata-backed live workspace blocks `create`, even with a different `--slug` or `--new`. A missing board cell is not proof the assignment is gone. `resume --board <ID> --repo <repo-id>` validates exact metadata ownership, Git registration/common directory, confined path, branch/base and nonlocked/nonprunable state, then retries initialization and nonoverwriting provisioning before updating the board. Failures preserve files, metadata/error and board linkage. No branch creation or reinitialization occurs during recovery. Missing registration with leftover directories/branches requires inspection; never delete leftovers automatically.

Multiple incomplete candidates require explicit user selection: `resume --board <ID> --repo <repo-id> --worktree <exact-path>`; only exact validated candidates qualify. A current linked assignment is preferred automatically; explicit selection can replace that repo's board link, not repurpose/delete other candidates. For a new task when managed workspaces exist, use `--reuse <BOARD-ID>` for an explicitly assigned shared scope, or ASK for a new workspace before `create ... --new`. The flag is capability, not proof of consent, and cannot bypass same-task recovery. With no existing managed workspace, initial creation remains allowed.

Claude Code reads `.claude/settings.json` only from the directory it is launched in, so creation and recovery give each new worktree its own generated settings (static denies/allows plus the guard hook), preserving any user keys. A settings file that does not parse fails closed and is left in place. The hook walks up from the launch directory to the nearest `guard.py`, so a project worktree uses its control checkout's guard and policy. `CLAUDE.md` files are loaded from ancestors, so worktrees need no copy.

New worktrees and recovery provision local ignored env files and QA navigation without overwriting; `env.py status --board <ID>` reports provisioning and `env.py sync --board <ID>` uses the same copier. Never print secrets or commit local files. Existing copied factories need an authorized newer-script deployment before this recovery CLI is available; choosing or recovering live leftovers is separate user authorization.

The PreToolUse hook (`guard.py hook`) applies the policy to every Bash, edit and read call: a deny blocks the call, an ask prompts the user, and an allow defers to Claude Code's own permission mode. `guard.py check-git -- "<command>"` and `guard.py check-delete -- "<command>"` run the same checks explicitly. A denial stops the operation; a pass does not grant missing user authorization. `guard.py check-repos` checks mapping and `guard.py check-policy` checks the generated settings. Do not bypass failures, route a blocked edit through the shell, or hand-edit the guard-owned settings keys; change `.claude/policies/git-policy.json` and run `guard.py check-policy --write`.

Verify proportionately, update essential docs, and report actual results. Stage and commit only with applicable user authorization, on the assigned nonprotected branch, preserving unrelated work. Existing merge conflicts are resolved in place; do not start or complete a merge as part of conflict resolution.

```bash
python3 .claude/skills/git-worktree/scripts/worktree.py verify <slug>
python3 .claude/skills/git-worktree/scripts/worktree.py handoff --board <ID>
```

Handoff prints root-relative review and lifecycle commands; it does not commit changes or advance board status. The human runs commands from the control root. After an authorized commit, require `verify` to pass with a clean tree and commits ahead of base, reviewed acceptance evidence and updated docs. Then the coordinator uses `board.py set-status <ID> "Pending Merge"` for every included row sharing the worktree. Include all those IDs in both merge preview and apply. Do not suggest apply while any included row is In Review or the branch is uncommitted; changing status alone cannot fix dirty/uncommitted work. Human merge preview/apply uses `merge --board <ID>` and `merge --board <ID> --apply`; full completion records outcomes and cleans up, while conflicts/partial multi-repo progress are preserved. Cleanup uses `cleanup --board <ID> --apply` only after merged/clean checks. Discard is a separate human-only permanent-loss decision with preview and explicit `--apply --discard`; never execute it unasked. Do not auto-create another workspace after merge.

`guard.py sync --repo <ID>` previews the supported harness copy; add `--apply` only with authorization. Project control repositories receive `agents`, `commands`, `skills`, `policies`, the harness ignore file, and generated `.claude/settings.json`. Apps receive no harness or generated `CLAUDE.md`; existing handwritten instructions remain untouched. Sync does not copy scope/catalog layers.

For a missing project, use `/factory-bootstrap` or `python3 .claude/skills/git-worktree/scripts/bootstrap.py project` from the factory root; default `project/`, optional factory-local `--destination <new-path>`. External destinations require explicit user approval first and `--allow-outside`. Never manually copy. It copies blank docs/manifest and ignored complete local tooling/devcontainer, initializes Git and stages only intended initial source/docs/manifest/ignore files for exactly one initial commit. Only the new-repo protected-branch/worktree context exception applies; hard command denials, hooks and local identity remain enforced without global policy/config changes. Existing repos/control registration edits are not auto-committed. Prerequisites/existing paths/symlinks/collisions are refused; failures retain partial state, never delete/reinitialize.

After cloning, run the factory checkout's script: `python3 /path/to/factory/.claude/skills/git-worktree/scripts/bootstrap.py restore --destination /path/to/project`. It rebuilds the ignored map from tracked `services.json` and restores harness/config/generated instructions/blank board/devcontainer. Clone separate services yourself at registered paths, then use `restore --destination /path/to/project/apps/shop-frontend --project /path/to/project`. Control must be restored first; canonical placement preserves existing control-root discovery. App restore inherits control tooling with ignored local instructions/config/harness, no app-local devcontainer or app map/board. Open the control folder in its devcontainer and work under `apps/<name>` so the whole control context is mounted. Relative `../../` instructions and ancestor board/map discovery survive different mount prefixes; the restored service settings resolve the control guard by walking ancestors. Existing app devcontainers are untouched and need manual review. Conflicting files and tracked outputs/ancestors cause refusal before tooling/exclude writes; identical files stay, missing files return. No force, network, init/add/commit, source/index/HEAD/config changes or install/build. Clone-local excludes protect tooling without source-ignore edits. Separate-app bootstrap enforces hard init/add/commit denials from both executing source and target control, retaining narrow initial-commit context exceptions and identity/hooks. Never run restore on the factory or a linked worktree. See README constraints. Existing projects/apps are not migrated.
