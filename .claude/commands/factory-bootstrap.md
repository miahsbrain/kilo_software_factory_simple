The user-chosen workspace is the boundary. Check CWD/source/resolved project destination and resolved control/app/worktree targets against the user's selection before creation or writes; stop on mismatch. Never infer destinations from product display/service names, enter siblings or reuse unrelated board/worktree paths without explicit approval. Project CWD must equal source factory root; relative destinations use CWD. Default is local `project/`, custom destinations must stay within the factory unless the user explicitly approves an external path first, then use `--allow-outside`. This flag is capability, not consent, and is invalid for app/restore. Restore's explicit external target remains supported without it; verify the approved clone.

Use the deterministic CLI, never manual copying. From the factory root run `python3 .claude/skills/git-worktree/scripts/bootstrap.py project` (default `project/`), or provide a factory-local `--destination <new-path>`. Project Git is mandatory. Follow `/factory-plan`'s exact approved service map: full NAME, explicit ROLE, sibling `apps/<full-name>` root, responsibility/stack and separate/project Git ownership; ASK actual unknown decisions. Do not collapse a planned multi-service product into one product-named folder or create unapproved services from technology alone. A planned React frontend plus Python API uses sibling `apps/camera-shop-frontend` and `apps/camera-shop-api`, not `apps/camera-shop-api/backend`. An approved single runtime can stay one role-named service. From the assigned linked control source worktree root run `python3 /path/to/control/.claude/skills/git-worktree/scripts/bootstrap.py app <product-role> --role <role> --git separate|project`, using the actual inherited primary-control or approved factory script. Both role and ownership are required; the full positional name must end in `-<role>` with a valid nonempty product prefix. Arbitrary safe lowercase kebab-case roles, including multiword roles, frontend/backend variants, workers and cronjobs are supported; no fixed slots or role enum. Neither role nor product is derived by the tool.

The new project's initial commit precedes board/task setup and the first assigned control worktree. Create/resume that assignment using the existing lifecycle; registration never creates a task/workspace or falls back to primary. It validates actual Git/common-directory/branch, active metadata and board linkage. Keep tracked `services.json`, project-owned app source and `.gitignore` edits in the source worktree; primary tracked files/index/HEAD remain untouched. Separate repos initialize only at Git's canonical primary-control `apps/<full-name>` after explicit target diagnostics match the approved assignment, never under the feature worktree. Inherit ignored primary config/harness; do not copy secrets/config unnecessarily.

Merge ignored canonical `.claude/repos.json` from known primary/source registrations and validated current canonical/source maps, preserving other branches' separate full-name IDs. Reject divergent ownership/paths, stale/noncanonical targets and existing/partial/symlink destinations before registration writes. Only the caller's local snapshot refreshes; lifecycle uses the canonical map. This operational union does not merge tracked manifests: restore still reads the persisted primary manifest after authorized registration merge/commit, never implicitly switches/merges branches or reconstructs unmerged registrations in a fresh clone.

Metadata-only backend bootstrap (.gitignore/Git/manifest) may happen before frontend-flow approval. It authorizes no backend framework source, dependencies, routes, persistence or integration until approval, except backend-only maintenance. Verify subsequent implementation assignment against the approved service and ownership.

Both modes preserve source/docs and ignore clone-local harness/config/devcontainer/generated root instructions/live board/secrets/outputs. `services.json` is the single tracked control manifest (name, path, separate/project ownership); `.claude/repos.json` is generated with control plus separate services only. Separate services get a safe ignore snapshot and one initial commit. Integrated services get the same ignores and a targeted control unignore, no nested Git/staging/control commit. Existing apps are not updated by later ignore edits.

Role is a creation-time intent check, not a manifest field: keep exactly name/path/git entries, recording operational role/topology in product docs. Existing legacy entries/restores remain readable without inference or renaming. Repo IDs stay full service names.

For a fresh clone invoke the factory checkout's script: `python3 /path/to/factory/.claude/skills/git-worktree/scripts/bootstrap.py restore --destination /path/to/project`. Clone separate services yourself into registered `apps/<service-name>` paths, then restore each with `restore --destination /path/to/project/apps/shop-frontend --project /path/to/project`. Restore control first; app tooling inherits it. No network, Git init/add/commit, source edits or overwrites. Missing files restored, identical left, any conflict refused before writes; no force flag. Missing checkouts are reported, not fabricated.

Restore refuses tracked output paths and all tracked ancestors before tooling/exclude writes. App restore creates no app-local devcontainer: open the control project folder in its devcontainer, then work under `apps/<name>`. Service instructions use relative `../../` context and lifecycle ancestor discovery, not host-absolute pointers. Claude Code loads ancestor `CLAUDE.md` files but reads `.claude/settings.json` only from the launch directory, so restore gives each service its own generated settings, and the guard hook there resolves the control guard. Existing app devcontainers remain untouched, not endorsed. Separate-app bootstrap checks hard init/add/commit denials in both source and target-control policies; allowances never override the other's denial.

Read `README.md` for constraints. User authorization covers exactly one initial source commit only in genuinely new project/separate-service repos created by the invocation. The narrow protected-branch/worktree bootstrap exception does not weaken policy, bypass hard command denials or skip hooks; honor existing identity. Existing destinations are refused. Identity preflight failure creates nothing; later failures retain partial state for inspection. No installs/scaffolding/existing-repo commits. Feature implementation waits for the initial commit and assigned worktree.
