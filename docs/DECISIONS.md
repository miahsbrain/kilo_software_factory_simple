# DECISIONS

Append-only. Ultra-concise approved architectural decisions. New rows go at the end.

## How to record a decision

- **Approved** — add a row to the table below with the date and the one-line reason.
- **Assumption** — add a row with `Status: ASSUMPTION — awaiting user confirmation` and list it
  in the handover's Open Questions. Replace it with the approved decision when confirmed.

| # | Decision | Context | Consequence | Date |
|---|---|---|---|---|
| ADR-001 | `AGENTS.md` lives at the repo root; all other docs live in `docs/` (except `DOMAIN.md`, `ROADMAP.md`, `CHANGELOG.md`) | Kilo auto-loads the root file; avoids scattered docs | Root is the only place for cross-project rules | 2026-10-29 |
| ADR-002 | Two changelogs: `docs/changelog/` (engineering, updated every change) and root `CHANGELOG.md` (product-facing, user-approved only) | Different audiences and cadences | Both must be kept in sync at release time | 2026-10-29 |
| ADR-003 | No git commits, amends, pushes, or PRs by any agent | User decision | Work is left in the worktree for user review and merge | 2026-10-29 |
| ADR-004 | Functional core / imperative shell, reuse-before-creation, minimal comments | User decision | Domain logic is pure and testable; codebase stays small | 2026-10-29 |
| ADR-005 | Every change happens in a worktree named after the feature (`.kilo/worktrees/<feature-slug>/`), never in the main checkout | User decision | Worktrees are the unit of work; each carries code + doc updates together | 2026-10-29 |
| ADR-006 | Board lanes are `Backlog → Ready → In Progress → In Review → Pending Merge → Merged`, plus `Blocked`/`Dropped` | super-board concept, adapted to a local markdown board | Works offline in the CLI; `Pending Merge` is the inspection gate before the user merges | 2026-10-29 |
| ADR-007 | Guard rules (worktree confinement, secrets, key literals, destructive scope, protected branch) live as markdown in `AGENTS.md`, not as hook scripts | Kilo has no hook runner | Rules are agent responsibilities rather than enforced tooling | 2026-10-29 |
| ADR-008 | Acceptance criteria are checkboxes with a proof line; evidence before prose | super-board writing standard | Prevents "done" claims that were never verified | 2026-10-29 |
| ADR-009 | Worktree naming uses the feature slug, not an issue number | User decision | Overrides super-board's `issue-<N>` convention | 2026-10-29 |
| ADR-010 | The live board lives in the main checkout and has a single writer: the orchestrator. Worktree branches never edit `docs/BOARD.md` | User decision — recommended option over branch-carried boards | The board shows in-flight work at all times and parallel worktrees cannot conflict on it. After a merge, the orchestrator marks the row `Merged` on `main` | 2026-10-29 |
| ADR-011 | The architect asks the user for implementation decisions before building anything, and never silently assumes product, data, contract, architecture, persistence, boundary, or operations choices | User decision | A decision sheet with a recommended option goes to the user; approved decisions travel with the builder prompt; unknowns escalate back instead of being guessed | 2026-10-29 |
| ADR-012 | Frontend work builds a component factory and a gallery route first; the user approves the visual language before any screen is built | User decision | Screens reuse approved components only; a deviation from the gallery is a review finding, not a new decision | 2026-10-29 |
| ADR-013 | The QA lane for frontend work uses Playwright and produces screenshot evidence; a UI/UX critique runs alongside it against 15 anti-slop rules | super-board concept, adapted; lean version | A frontend row cannot leave `In Review` until both are green; artifacts under `artifacts/<scope>/qa/` | 2026-10-29 |
| ADR-014 | `.kilo/command/*.md` are derived artifacts of `AGENTS.md`, not independent rules | User decision | A rule change updates the matching command in the same change; `AGENTS.md` wins on conflict | 2026-10-29 |
| ADR-015 | Builders commit locally on their worktree branch; agents never push, never merge into `main`, never open a PR | The previous "never commit" rule left nothing for the user to merge | The user merges; local commits make the merge real and reviewable | 2026-10-29 |
| ADR-016 | Dedicated agents in `.kilo/agent/`: `frontend-dev`, `backend-dev`, `mobile-dev`, `qa-reviewer`, `ui-critic` | User request for a multi-agent team | Builders and reviewers each carry their own scope, style, verification, and reporting rules | 2026-10-29 |
| ADR-017 | QA and UI/UX findings become board rows of type `Fix`, written by the orchestrator from the review reports | User request | Reviews are independent of the builder's claims; the board keeps a single writer | 2026-10-29 |
| ADR-018 | CLI only — plain `git`, no `gh`, no extension, no pull requests | User request | Work lands through local branches and human merges; no remote workflow to depend on | 2026-10-29 |
| ADR-019 | The worktree procedure is a Kilo skill at `.kilo/skills/git-worktree/SKILL.md` | User request, modelled on the super-board worktree skill | The rules in `AGENTS.md` have an executable CLI procedure beside them | 2026-10-29 |
| ADR-020 | Agents never commit to `main`/`master`/`base` and never commit to a branch that already has a worktree; one branch, one worktree, one task | User request | The base branch and existing branches stay under human control | 2026-10-29 |
| ADR-021 | `Pending Merge` means waiting for human approval to merge, into `main` or a feature branch | User request | The merge target is the human's decision; the agent only prepares and reports | 2026-10-29 |
| ADR-022 | Deterministic scripts own the mechanics; agents own the judgment. Worktrees, board rows, QA capture, finding validation, and destructive-command checks all run through scripts in `.kilo/skills/*/scripts/` | Ported from super-board's agent-writes-evidence / script-writes-machinery split | Rules that can be enforced by a script are enforced, not trusted | 2026-10-29 |
| ADR-023 | Deletion is allowed only inside the current linked worktree or a temp dir; the main checkout, `/`, and `$HOME` are never deletable | User request, stricter than upstream | `guard.py check-delete` enforces it before any destructive command | 2026-10-29 |
| ADR-024 | The board is edited with `board.py`, never by hand | Ported from super-board's card script | One writer, one parser, atomic writes; no corrupted table rows | 2026-10-29 |
| ADR-025 | A QA finding must pass `check-finding.py` before it becomes a board row | Ported from super-board's ticket body validation | A weak finding that names no expected behavior, repro, or evidence is refused | 2026-10-29 |
| ADR-026 | The worktree name and branch type are derived from the board row, never typed by hand | User request | `Feature` → `feat/`, `Fix` → `fix/`, `Chore` → `chore/`, `Docs` → `docs/`; the slug comes from the task title. A bug fix can no longer land on `feat/…` | 2026-10-29 |
| ADR-027 | `worktree.py create` writes the board row in the main checkout, resolved via `git worktree list --porcelain` | Single-writer rule (ADR-010) | A worktree branch never carries a board edit; the live board always points at the running worktree | 2026-10-29 |
| ADR-028 | The build lanes form a loop that runs until the spec is met: a row cannot reach `Pending Merge` while a Fix row it spawned is open, every Fix row runs the same lanes, and the original row is re-verified after the fixes merge | User request — the pipeline had lanes but no closure | "The builder finished" is not a stopping condition; "every acceptance criterion passes with proof" is | 2026-10-29 |
| ADR-029 | Reuse-before-creation is reported, not assumed: the builder's report names the existing code it found, the verdict, and what is new | User request — the rule existed but was unverifiable | The Review lane can check it, and a Feature row carries a reuse acceptance criterion | 2026-10-29 |
| ADR-030 | "Modern" and "user-centred" are checkable criteria in `docs/UI-UX.md` §3 — U1–U8 and M1–M10 — enforced by both the QA lane and the UI/UX critique | User request — the anti-slop rules covered looks, not usefulness | A screen can pass every aesthetic rule and still be a bad product; that is now a FAIL | 2026-10-29 |
| ADR-031 | A read-only board viewer serves the lanes, cards, and live worktree state on port 15180 | User request — the markdown table is hard to scan | The board is still the source of truth; the dashboard only renders it, and re-reads it on every request | 2026-10-29 |
| ADR-032 | `board.py` refuses a cell value containing a newline or a raw pipe | A multi-line note broke the markdown table and left orphan rows | The board cannot be corrupted by a value that was supposed to be one line | 2026-10-29 |
| ADR-033 | Worktree slugs drop trailing connective words after the 6-word cap | The cap cut titles mid-phrase ("…dashboard-with") | The branch name reads as the feature or bug it fixes | 2026-10-29 |
| ADR-034 | The Playwright MCP is configured in `kilo.jsonc` and the QA script resolves Playwright from the global install the devcontainer provides | The MCP was installed but never configured, so agents had no browser tools and fell back to ad-hoc bash | One tool owns the evidence: `browser-review.mjs` for captures, the MCP for interactive investigation | 2026-10-29 |
| ADR-035 | A verification must yield a binary signal, two attempts per check, and the subject of a verification is never mutated | A builder looped for an hour on checks that could not return pass/fail | An ambiguous check is reported as a limitation once, not iterated on | 2026-10-29 |
| ADR-036 | The QA↔fix loop is capped at 3 rounds, a repeat finding escalates the existing row instead of opening another, and a ledger carries the state between rounds | The UI critique → fix loop could run forever | The loop terminates on the spec, and a repeat is a signal to ask the human | 2026-10-29 |
| ADR-037 | One canonical artifacts folder at the repository root: `artifacts/<scope>/qa/<date>/<task-id>/`; the capture script computes the path itself and review reports and ledgers stay in `docs/reviews/` | UI evidence was scattered across app folders, `docs/`, and `/tmp` | One place to look for evidence; the script owns the layout so no agent has to remember it | 2026-10-29 |
| ADR-038 | An agent checks what exists — skills, MCP servers, global tools, standard library, repo scripts — and then asks before building a tool | An agent wrote its own browser client while Playwright was installed globally | A custom tool is a project-sized decision, not a local workaround | 2026-10-29 |
| ADR-039 | The QA capture path drives Playwright only — no CDP client, no second driver; a missing chromium is reported (exit 2), never installed or replaced; and a failed command, capture, or test is reported instead of routed around | An agent built a browser client by hand instead of asking, and the capture script advertised a CDP fallback that did not exist | One driver owns the evidence, and a missing browser, package, or system tool stays the user's decision | 2026-10-29 |
| ADR-040 | The guard rails live in one policy file that feeds two layers: the generated `permission` map in `kilo.jsonc` and `guard.py check-git`, which adds the context checks a keyword list cannot see | A keyword list cannot tell a commit on `main` from a commit on a worktree branch, and two copies of the rules drift apart | One file to edit, a check that proves the layers match, and the user's approval required for anything irreversible | 2026-10-30 |
| ADR-041 | A `docs-writer` agent owns the application memory map: it reads the whole codebase on its first run in a session and writes one handover per unit plus a global index under `docs/handover/`, marking every module pure, reactive or effectful | A handover written from memory of a system drifts, and a reader cannot tell which parts are pure and which touch the outside world | One agent owns the map, every claim carries a `file:line`, and the index lists every unit | 2026-10-30 |
| ADR-042 | A repo is addressed by an id from `.kilo/repos.json`, never by a raw path; the control repo owns the board, the docs, the policy and the agents, and an app repo under `apps/` is a work surface that receives the same guard rails through `guard.py sync` | User request (BOARD-003) | One map is the only way into a repository, so a worktree, a sync and a board row all name the same repo the same way; the guard rails stay identical in every repo | 2026-10-30 |
