## Bootstrap

The factory creates this control repository with `python3 .claude/skills/git-worktree/scripts/bootstrap.py project` from its checkout root (default `project/`; optional `--destination <new-path>`). Use the CLI, not manual copying. It copies blank documents and complete local tooling/devcontainer, initializes Git and creates one initial source commit. Track source, product docs, `.gitignore` and `services.json`. `.claude/` (including generated `settings.json`), `.devcontainer/`, generated root `CLAUDE.md`, live `docs/BOARD.md`, secrets and outputs are ignored. The factory tracks its template board/harness, not copied live state.

Project CWD must equal the executing source factory root, without fallback; relative destinations use CWD. Default layout is `/path/to/factory/project/apps/`, never a sibling inferred from a display/service name. Custom internal destinations with existing real parents are supported. CWD/source/resolved destination print to stderr before creation; external project targets are refused before any writes or Git mutations by default. ONLY after actual user approval, from the factory root: `python3 .claude/skills/git-worktree/scripts/bootstrap.py project --destination /path/to/approved-project --allow-outside`. The flag is capability, not consent; traversal/symlinks remain refused. App/restore reject it; restore still accepts explicit external clones without it. Verify resolved control/target roots against the user-chosen workspace before app/worktree writes and stop on mismatch; do not enter siblings or reuse unrelated boards/worktrees without approval. Lifecycle helpers may still run from legitimate app/feature worktrees.

After the project's initial commit, record the task on the live board and create/resume its assigned linked control source worktree using the lifecycle tools. From that worktree root, register approved services using the actual inherited primary-control (or approved factory) script path; do not copy config/secrets/tooling just to run it:

```bash
python3 /path/to/control/.claude/skills/git-worktree/scripts/bootstrap.py app camera-shop-frontend --role frontend --git separate
python3 /path/to/control/.claude/skills/git-worktree/scripts/bootstrap.py app camera-shop-api --role api --git project
python3 /path/to/control/.claude/skills/git-worktree/scripts/bootstrap.py app billing-worker --role worker --git project
python3 /path/to/control/.claude/skills/git-worktree/scripts/bootstrap.py app inventory-stock-worker --role stock-worker --git project
```

Project Git is mandatory; role (`--role <role>`) and ownership (`--git separate|project`) are independently required with no defaults. The positional name stays the full service name: it must end in `-<role>` with a nonempty valid product prefix. Both prefix and role start with a lowercase letter and use lowercase kebab-case; arbitrary roles, multiword roles and frontend/backend variants are supported, not a role enum. The tool derives neither product nor role. Product-only `camera-shop --role frontend`, bare `frontend --role frontend`, mismatches and unsafe prefixes/roles reject before manifest reads or writes. Selected role and full target are reported without secrets. Separate mode initializes Git and commits only its initial `.gitignore`. Project mode creates no nested repo/staging/control commit, adding a targeted unignore for `apps/<service-name>`. Both update tracked `services.json` with name/path/git ownership; the ignored generated `.claude/repos.json` contains only control plus separate services with full-name repo IDs. Control registration changes require a separate authorized commit. No scaffolding/install. Existing paths, unsafe paths, invalid manifests/maps and collisions are refused.

Before bootstrap, `/factory-plan` hands off the approved service map in product docs: each full NAME, explicit ROLE, sibling `apps/<full-name>` root, responsibility/stack and separate/project Git ownership. Ask actual unknown decisions. A planned React frontend plus Python API uses sibling `apps/camera-shop-frontend` and `apps/camera-shop-api`, not product-only `apps/camera-shop` or nested `apps/camera-shop-api/backend`. Check no approved service was collapsed or omitted, without inferring unapproved services from technology alone; one approved runtime may remain one role-named service. `/factory-bootstrap` follows this exact map; `/factory-run` verifies the correct service assignment, using control's worktree for project ownership or the full-name mapped worktree for separate ownership.

Both modes snapshot project ignores without control-only service-directory rules, explicitly protecting local harness/config/devcontainer/instructions/live board/secrets/outputs while source/docs/`.env.example` stay trackable. Later ignore edits do not automatically refresh snapshots. `services.json` starts as `{"services":[]}`; entries use `{"name":"shop-backend","path":"apps/shop-backend","git":"separate"}` (or `project`). It is the only tracked ownership manifest.

Role is a creation-time intent check, not a persisted field. Preserve this exact three-field manifest, recording operational roles/topology in product docs instead. Legacy entries/restores remain readable without inference, renaming or migration; no new planning registry. The check cannot prove prose-plan completeness, and older copied tools require authorized deployment to enforce it.

Requires Python 3.9+ and Git; unset `GIT_*` overrides. User approval covers exactly one initial commit only in new project/separate-service repos created by the command. It stages intended initial files, requires an unborn HEAD/empty index, honors Git identity/hooks and hard command-policy denials, and narrowly exempts initial commits from protected-branch/worktree context checks without changing policy. No identity invention or hook skipping. Identity preflight failure creates nothing; later failures retain partial state/index and report failure. Inspect rather than delete/reinitialize. Existing repos and project-owned services are never auto-committed. Feature source implementation still requires an assigned linked worktree.

Registration validates board linkage, active lifecycle metadata and Git/common-directory/branch assignment. Primary and unassigned callers must create/resume their linked control assignment; no primary fallback or automatic task/workspace creation. Tracked `services.json`, project-owned app source and targeted `.gitignore` edits stay in the assigned source. Separate repos retain canonical primary-control `apps/<full-name>` roots, derived from Git, not from the source worktree directory; verify printed canonical target diagnostics against the approved assignment before initialization. Conflicting ownership/paths, stale/noncanonical maps and existing/partial/symlink targets refuse before registration writes. This is an operational union, not a tracked cross-branch manifest merge. Only the caller's local snapshot refreshes; lifecycle uses the canonical map. ## Restore A Clone

Use the factory checkout's script, since tooling is intentionally untracked here:

```bash
python3 /path/to/factory/.claude/skills/git-worktree/scripts/bootstrap.py restore --destination /path/to/project
# Clone separate services yourself into their registered paths, then:
python3 /path/to/factory/.claude/skills/git-worktree/scripts/bootstrap.py restore --destination /path/to/project/apps/shop-frontend --project /path/to/project
```

Restore control first; missing service checkouts are reported. App restore requires its registered `apps/<name>` location and explicit control context unless safely inferable there. It inherits the control harness with ignored local tooling/config/instructions, no app-local devcontainer or duplicate app map/board. Open this control project's folder in its devcontainer, then work under `apps/<name>`; an app-only mount hides control. Instructions use relative `../../` context and tools discover the ancestor board/map; the app's restored `.claude/settings.json` resolves the control guard, since Claude Code reads settings only from its launch directory. Existing app devcontainers are left untouched and require manual review; use the control container for supported tooling. No network or fabricated remotes. Restore checks all outputs and tracked ancestors first: missing files restored, identical left, tracked paths/ancestors or differing custom/generated files refused without writes. No force option, source/`.gitignore` edits, init/add/commit, config changes, installs or image builds. Clone-local excludes ignore tooling. Symlinks/traversal, factories, linked worktrees, malformed manifests and missing factory source roots are refused. The control-level generated devcontainer keeps supported Dockerfile/features/env/ports with only local shell-guard post-create setup, not the factory's global Git/doctor step. Separate-app bootstrap honors hard init/add/commit denials from both the executing source and this target control's policy; neither can relax the other.
