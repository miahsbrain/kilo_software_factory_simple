# Git Worktree

Anchor writes to the user-approved workspace: verify resolved control and target repo/worktree/app roots against the assignment before mutation; stop on mismatch. Never enter siblings, infer destinations from display/service names or reuse unrelated board/worktree paths without explicit approval. Lifecycle helpers may still run from app/feature worktrees and restore from the factory. Project creation alone requires source factory-root CWD, defaults to local `project/`, and requires actual user approval before external `--destination` plus project-only `--allow-outside` (capability, not consent).

Use the assigned workspace for implementation, docs, fixes, and review. All FEATURE implementation requires an assigned linked worktree, not the primary checkout. Explicitly assigned features may share that worktree and branch; preserve scope/ownership and never auto-switch branches. Inspect existing links before creating anything. Tracked `services.json` records only service names/paths/Git ownership; ignored `.kilo/repos.json` maps control plus actual separate repos using full service-name IDs. Project Git is mandatory; service ownership and role are explicit: follow the approved plan's full name, role, sibling `apps/<full-name>` root, responsibility/stack and separate/project ownership, asking actual unknown decisions. Use `bootstrap.py app <product-role> --role <role> --git separate|project` from the assigned linked control source worktree root, invoking the actual inherited primary-control or approved factory script path. Names must end in `-<role>` with a valid nonempty product prefix; any safe lowercase kebab-case role is supported, including multiword roles, not an enum. Do not collapse planned services or infer unapproved services from technology. Separate mode initializes/initial-commits/maps; project mode has no nested Git/staging/control commit and adds a targeted source unignore. Both register ownership in the unchanged three-field manifest; operational topology/roles belong in product docs, not a registry. Legacy entries/restores are not renamed or inferred. Verify implementation assignment: project-tracked services use control's worktree; separate services their full-name mapped worktree.

New-project metadata gets its initial commit before the first board/task control assignment. Create/resume that linked assignment with this lifecycle before registering apps; bootstrap checks board linkage, active metadata and actual Git/common-directory/branch identity, never creates assignments or falls back to primary. Tracked `services.json`, project-owned app source and targeted `.gitignore` edits stay source-local; primary tracked files/index/HEAD stay untouched. Separate repos retain Git-derived canonical primary-control `apps/<full-name>` roots, never feature-worktree nested repos: check printed canonical targets against the approved assignment first. Inherit ignored config/harness; do not copy secrets/config just to invoke bootstrap.

Registration safely unions ignored canonical/source maps and primary/source manifest registrations, retaining other branches' separate full-name IDs. Divergent ownership/paths, stale/noncanonical maps and existing/partial/symlink targets refuse before writes. Only the caller's local snapshot refreshes; lifecycle resolves against the canonical map. This is not a tracked manifest merge: restore uses the persisted primary manifest after an explicitly authorized registration merge/commit, never switches/merges branches implicitly, and fresh clones do not recover unmerged registrations from ignored maps.

Use the existing scripts from the control root:

Both modes write safe app-local project-ignore snapshots without control service-directory rules. Source/docs remain trackable; harness/config/devcontainer/generated root instructions/live board/secrets/outputs stay local ignored. Later ignore changes do not automatically refresh snapshots.

```bash
python3 .kilo/skills/git-worktree/scripts/worktree.py mode status
python3 .kilo/skills/git-worktree/scripts/worktree.py list
python3 .kilo/skills/git-worktree/scripts/worktree.py resume --board <ID>
python3 .kilo/skills/git-worktree/scripts/worktree.py create --board <ID> --repo <repo-id> --base <branch>
python3 .kilo/skills/git-worktree/scripts/worktree.py create --board <NEW-ID> --reuse <EXISTING-ID> --repo <repo-id>
```

Create only an authorized workspace. `--reuse` supports Feature rows as well as Fix rows, retaining the existing branch/base and recording the new assignment; it does not require one worktree per feature. Required mode uses linked `.kilo/worktrees/`; optional mode permits an assigned nonprotected current checkout for non-feature maintenance only; adaptive mode requires worktrees for Feature rows but treats Fix/Chore/Docs as optional (use current checkout allowed). Do not change saved mode or permissions to encode feature assignment. Changing mode regenerates permissions and requires a Kilo restart. Bootstrap creates the user-authorized initial source commit only in genuinely new repositories created by that invocation, before linked worktrees become usable; feature implementation waits for successful initialization and assignment.

Reuse first: the same task's metadata-backed live workspace blocks `create`, even with a different `--slug` or `--new`. A missing board cell is not proof the assignment is gone. `resume --board <ID> --repo <repo-id>` validates exact metadata ownership, Git registration/common directory, confined path, branch/base and nonlocked/nonprunable state, then retries initialization and nonoverwriting provisioning before updating the board. Failures preserve files, metadata/error and board linkage. No branch creation or reinitialization occurs during recovery. Missing registration with leftover directories/branches requires inspection; never delete leftovers automatically.

Multiple incomplete candidates require explicit user selection: `resume --board <ID> --repo <repo-id> --worktree <exact-path>`; only exact validated candidates qualify. A current linked assignment is preferred automatically; explicit selection can replace that repo's board link, not repurpose/delete other candidates. For a new task when managed workspaces exist, use `--reuse <BOARD-ID>` for an explicitly assigned shared scope, or ASK for a new workspace before `create ... --new`. The flag is capability, not proof of consent, and cannot bypass same-task recovery. With no existing managed workspace, initial creation remains allowed.

Ignored control config is inherited from eligible ancestors inside the actual control root, never an unrelated source factory. Creation/recovery validates inherited ordered permission maps against saved mode without regenerating them; valid local manual config is respected. Missing config, invalid protections or out-of-scope `KILO_CONFIG` fail closed. Mode transitions handle ignored local configs without requiring or creating an empty/full copied config.

New worktrees and recovery provision local ignored env files and QA navigation without overwriting; `env.py status --board <ID>` reports provisioning and `env.py sync --board <ID>` uses the same copier. Never print secrets or commit local files. Existing copied factories need an authorized newer-script deployment before this recovery CLI is available; choosing or recovering live leftovers is separate user authorization.

Before a mutating Git command or destructive shell operation, use `guard.py check-git -- "<command>"` or `guard.py check-delete -- "<command>"`. A denial stops the operation; a guard pass does not grant missing user authorization. `guard.py check-repos` checks mapping and `guard.py check-policy` checks generated permissions. Do not bypass failures or hand-edit the generated permission block.

Verify proportionately, update essential docs, and report actual results. Stage and commit only with applicable user authorization, on the assigned nonprotected branch, preserving unrelated work. Existing merge conflicts are resolved in place; do not start or complete a merge as part of conflict resolution.

```bash
python3 .kilo/skills/git-worktree/scripts/worktree.py verify <slug>
python3 .kilo/skills/git-worktree/scripts/worktree.py handoff --board <ID>
```

Handoff prints root-relative review and lifecycle commands; it does not commit changes or advance board status. The human runs commands from the control root. After an authorized commit, require `verify` to pass with a clean tree and commits ahead of base, reviewed acceptance evidence and updated docs. Then the coordinator uses `board.py set-status <ID> "Pending Merge"` for every included row sharing the worktree. Include all those IDs in both merge preview and apply. Do not suggest apply while any included row is In Review or the branch is uncommitted; changing status alone cannot fix dirty/uncommitted work. Human merge preview/apply uses `merge --board <ID>` and `merge --board <ID> --apply`; full completion records outcomes and cleans up, while conflicts/partial multi-repo progress are preserved. Cleanup uses `cleanup --board <ID> --apply` only after merged/clean checks. Discard is a separate human-only permanent-loss decision with preview and explicit `--apply --discard`; never execute it unasked. Do not auto-create another workspace after merge.

`guard.py sync --repo <ID>` previews the supported harness copy; add `--apply` only with authorization. Project control repositories receive `agent`, `command`, `skills`, `policies`, the harness ignore file, and generated permissions. Apps inherit local config without receiving another harness or generated `AGENTS.md`; existing handwritten instructions remain untouched. Sync does not copy scope/catalog layers.

For a missing project, use `/bootstrap` or `python3 .kilo/skills/git-worktree/scripts/bootstrap.py project` from the factory root; default `project/`, optional factory-local `--destination <new-path>`. External destinations require explicit user approval first and `--allow-outside`. Never manually copy. It copies blank docs/manifest and ignored complete local tooling/devcontainer, initializes Git and stages only intended initial source/docs/manifest/ignore files for exactly one initial commit. Only the new-repo protected-branch/worktree context exception applies; hard command denials, hooks and local identity remain enforced without global policy/config changes. Existing repos/control registration edits are not auto-committed. Prerequisites/existing paths/symlinks/collisions are refused; failures retain partial state, never delete/reinitialize.

After cloning, run the factory checkout's script: `python3 /path/to/factory/.kilo/skills/git-worktree/scripts/bootstrap.py restore --destination /path/to/project`. It rebuilds the ignored map from tracked `services.json` and restores harness/config/generated instructions/blank board/devcontainer. Clone separate services yourself at registered paths, then use `restore --destination /path/to/project/apps/shop-frontend --project /path/to/project`. Control must be restored first; canonical placement preserves existing control-root discovery. App restore inherits control tooling with ignored local instructions/config/harness, no app-local devcontainer or app map/board. Open the control folder in its devcontainer and work under `apps/<name>` so the whole control context is mounted. Relative `../../` instructions and ancestor board/map discovery survive different mount prefixes; control `KILO_CONFIG` is workspace-relative. Existing app devcontainers are untouched and need manual review. Conflicting files and tracked outputs/ancestors cause refusal before tooling/exclude writes; identical files stay, missing files return. No force, network, init/add/commit, source/index/HEAD/config changes or install/build. Clone-local excludes protect tooling without source-ignore edits. Separate-app bootstrap enforces hard init/add/commit denials from both executing source and target control, retaining narrow initial-commit context exceptions and identity/hooks. Never run restore on the factory or a linked worktree. See README constraints. Existing projects/apps are not migrated.
