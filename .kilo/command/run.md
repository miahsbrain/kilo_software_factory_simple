For a feature, read the shared implementation plan linked in the board Notes before starting or resuming. Resolve it against the owning primary control checkout, not the current service. Pass its absolute path, phase and acceptance criteria to every implementation agent. If it is missing, resolve the plan with the coordinator instead of creating a second copy.

Read the row and relevant context. Use its assigned workspace and existing lifecycle tools; keep the board current through the coordinator. Implement the smallest sound solution, using specialists through short explicit assignments when useful. For new apps and user-facing features, get frontend-flow approval before backend work; fixtures must be labeled.

Follow the exact approved service map from `/plan`: full name, role, sibling `apps/<full-name>` root, responsibility/stack and separate/project ownership. Resolve missing material decisions, never infer unapproved services or collapse a planned multi-service product into one folder. Bootstrap with `bootstrap.py app <product-role> --role <role> --git separate|project`; verify the implementation assignment targets that service (control worktree for project ownership, full-name repo ID for separate). Metadata-only backend bootstrap (.gitignore/Git/manifest) may precede frontend-flow approval; backend framework source, dependencies, routes, persistence and integration may not, except backend-only maintenance.

Reuse the same task's assigned worktree. Missing board linkage may be incomplete creation: `resume --board ID --repo ID` validates metadata and retries initialization/provisioning before linking. Ambiguous candidates need user selection with `--worktree PATH`; preserve the others. Never retry another slug. New tasks with managed workspaces require explicit `--reuse ID`, or ASK before `--new` (capability, not consent); it cannot bypass same-task recovery. Truly missing assignments with leftover directories/branches require inspection, not deletion or branch reinitialization.

Treat the user-chosen workspace as the boundary: verify resolved control and target roots against the assignment before bootstrap/app/worktree writes; stop on mismatch. Never enter a sibling, infer paths from display/service names or reuse unrelated board/worktree paths without explicit user approval. Factory-root project bootstrap defaults to local `project/`; ASK before an external destination, then use project-only `--allow-outside`, which does not itself establish approval. This is a root/assignment check, not a blanket CWD restriction on lifecycle helpers or factory-sourced restore.

All FEATURE implementation uses an assigned linked worktree, never the primary checkout, regardless of optional maintenance policy. Explicitly assigned features may share the same worktree/branch with `worktree.py create --board NEW --reuse EXISTING --repo ID`; preserve scope/ownership and do not auto-switch branches or change permissions/mode. Project-tracked apps use control's worktree; separate apps use their mapped repo's worktree. Metadata-only bootstrap is exempt: bootstrap makes the authorized initial commit only in new project/separate-service repositories it creates. Feature implementation then uses an assigned linked worktree; never auto-commit an existing repository.

For explicitly assigned current-checkout Fix/Chore/Docs work, check `worktree.py mode status` and run `worktree.py create --board ID --repo REPO --skip-worktree` from that checkout. This read-only preflight does not grant permissions or create a mergeable assignment. Required mode refuses it; adaptive mode still asks for ordinary primary edits and refuses primary commits. Use a linked workspace from the outset when adaptive work needs a commit.

Run normal code tests appropriate to the change. Before delegating review, check `worktree.py reviews status` from the assigned root; specialists must recheck. Delegate automated QA only for `qa: true` and critique only for `ui: true`. If QA is off, `/ui` uses existing evidence only. Invalid or unavailable policy means manual review for both. Consolidate findings once, fix meaningful defects, and recheck within policy. Update essential docs and report changes, actual checks, and limitations. No unauthorized staging, commits, destructive operations, merge, or push. Use the lifecycle handoff when ready for human review.

Register services in the assigned linked control worktree; tracked `services.json`, project-owned app source and ignore changes never go to primary. Separate app repositories remain at canonical primary-control `apps/<full-name>`; only ignored operational maps and shared coordination may update primary. Keep review output in the assigned root's ignored `artifacts/`. For saved browser evidence use only the existing runner from that root, never Playwright MCP or ad-hoc saving.
Read scoped manual review evidence with `board.py show <ID>` before asking the user to repeat a decision. Proceed only within the existing assignment; a review marker clears neither unrelated blockers nor authorization requirements.

At completion link the QA skill's manual QA/UI checklist for any skipped scope, even without a blocker, and for inaccessible criteria. Report verified results separately; a checklist is not a pass or lane transition.
